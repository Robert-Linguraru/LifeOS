# 1. Application Layers

## 1.1 Purpose

This document defines the internal application structure of LifeOS.

It bridges the gap between the Technical Architecture and the implementation by defining:

- application layers;
- dependency direction;
- layer responsibilities;
- service ownership;
- repository responsibilities;
- request flow boundaries.

The objective is to ensure every feature is implemented consistently throughout the lifetime of the project.

---

# 2. Architectural Philosophy

LifeOS follows a layered Clean Architecture approach.

Core principles:

- Dependencies always point inward.
- Business rules are independent of the UI.
- Infrastructure implements technology concerns only.
- Presentation never contains business logic.
- Every feature follows the same architectural pattern.
- Future modules should integrate into the existing architecture without requiring structural redesign.

# 8. Repository Responsibilities

Repositories are responsible for:

- CRUD operations
- Query execution
- Persistence
- Loading related entities
- Returning domain entities

Repositories must NOT:

- Calculate XP
- Calculate streaks
- Calculate finance summaries
- Generate dashboard models
- Contain business workflows

---

# 9. Cross-Cutting Services

Available throughout the application through Dependency Injection.

- ICurrentUserService
- IDateTimeProvider
- ILogger<T>
- IClock
- IConfiguration

These services must remain stateless where practical.

---

# 10. Architectural Rules

The following rules are mandatory throughout the project.

1. UI never contains business logic.

2. UI never writes directly to DbContext for feature workflows.

3. Every business workflow passes through an Application Service.

4. Every personal entity is user-scoped.

5. Business rules live inside Application Services.

6. Infrastructure implements technology, not business.

7. Domain remains independent of UI and Infrastructure.

8. Dashboard aggregates data but owns no business logic.

9. Repository classes remain persistence-only.

10. All future modules must follow the same architecture.
