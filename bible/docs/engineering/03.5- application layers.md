# 1. Application Layers

## 1.1 Purpose

This document defines the internal application structure of LifeOS.

It bridges the gap between the Technical Architecture and the implementation by defining:

- application layers;
- dependency direction;
- layer responsibilities;
- service ownership;
- repository responsibilities;
- request flow boundaries.

The objective is to ensure every feature is implemented consistently throughout the lifetime of the project.

---

# 2. Architectural Philosophy

LifeOS follows a layered Clean Architecture approach.

Core principles:

- Dependencies always point inward.
- Business rules are independent of the UI.
- Infrastructure implements persistence and service workflows behind Core contracts.
- Presentation never contains business logic.
- Every feature follows the same architectural pattern.
- Future modules should integrate into the existing architecture without requiring structural redesign.

There is no `LifeOS.Application` project. Service contracts, DTOs, validation rules, and application exceptions live in `LifeOS.Core`; EF-backed repositories and service implementations live in `LifeOS.Infrastructure`.

### Responsibilities

- Service contracts and implementations
- DTOs
- Validation
- Use Cases
- Workflow orchestration
- Transactions
- Mapping
- Business orchestration
- Returning View Models / DTOs

### Contains

Services

- TaskService
- HabitService
- ReminderService
- NotificationService
- XPService
- FinanceService
- DashboardService
- SettingsService

DTOs

- Create DTOs
- Update DTOs
- Details DTOs
- Summary DTOs
- Dashboard DTOs

Validators

- Feature validators
- Business validation

Interfaces

- Service and repository interfaces where required, in `LifeOS.Core`

### Must NOT

- Render UI
- Contain Razor Components
- Configure EF Core
- Contain SQL

Infrastructure service implementations may contain application/business workflows, validation, ownership coordination, lifecycle rules, and calculations such as Habit streaks. They implement service contracts defined in `LifeOS.Core`; repositories remain persistence-only. This reflects the current three-project architecture and does not require a separate Application project.

# 7. Service Dependency Rules

## TaskService

Allowed

- Task Repository
- ICurrentUserService
- IDateTimeProvider

Milestone 3 must not depend on XP, reminder, or notification services. Those integrations are added only by their owning later milestones.

Forbidden

- DashboardService
- FinanceService
- AIService
- WorkoutService

---

## HabitService

Allowed

- Habit Repository
- ICurrentUserService
- IUserSettingsService
- IDateTimeProvider
- ILogger<HabitService>

Forbidden

- DashboardService
- FinanceService
- XPService during Milestone 4
- ReminderService during Milestone 4
- Notification services during Milestone 4

XP integration belongs to Milestone 5. Reminder and notification integration belongs to Milestone 6.

---

## ReminderService

Allowed

- Reminder Repository
- NotificationService

Forbidden

- DashboardService

---

## NotificationService

Allowed

- Notification Repository

Forbidden

- DashboardService

---

## XPService

Allowed

- XP Repository
- UserProgression Repository
- NotificationService

Forbidden

- TaskRepository
- HabitRepository
- FinanceRepository

XPService receives business events only.

It never queries task or habit data directly.

---

## FinanceService

Allowed

- Finance Repository

Forbidden

- TaskService
- HabitService
- XPService

## DashboardService

Allowed

- TaskService for the Milestone 3 task widget
- HabitService for the Milestone 4 Habit widget

Later module services are added only when their slices are implemented.

DashboardService owns no business rules.

Its responsibility is aggregation only.

# 8. Repository Responsibilities

Repositories are responsible for:

- CRUD operations
- Query execution
- Persistence
- Loading related entities
- Returning domain entities

Repositories must NOT:

- Calculate XP
- Calculate streaks
- Calculate finance summaries
- Generate dashboard models
- Contain business workflows

---

# 9. Cross-Cutting Services

Available throughout the application through Dependency Injection.

- ICurrentUserService
- IDateTimeProvider
- ILogger<T>
- IConfiguration

These services must remain stateless where practical.

---

# 10. Architectural Rules

The following rules are mandatory throughout the project.

1. UI never contains business logic.

2. UI never writes directly to DbContext for feature workflows.

3. Every business workflow passes through a Core service contract implemented by Infrastructure.

4. Every personal entity is user-scoped.

5. Business rules live inside service implementations in Infrastructure, behind contracts defined in Core.

6. Repositories implement persistence only; Infrastructure services own application/business workflows.

7. Domain remains independent of UI and Infrastructure.

8. Dashboard aggregates data but owns no business logic.

9. Repository classes remain persistence-only.

10. All future modules must follow the same architecture.
